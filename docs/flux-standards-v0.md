# Flux Standards Process (FIPs) v0

> **One-line:** BIP-style improvement-proposal process for the Flux substrate — every standard is simultaneously a Markdown doc, a LaTeX-rendered PDF, an executable Flux API contract, and a SAP-scored quality artifact. SIGIL (and every future Flux-substrate chain) adopts FIPs as its own standards baseline.

## Why a process

The Flux Foundation deck shows what we sell: an AI-native, post-quantum, self-hosted build orchestrator. The deck doesn't yet tell buyers *how change happens* — who proposes, who reviews, how compatibility breaks are tracked, how SIGIL knows it's running a Flux-conformant stack. FIPs (Flux Improvement Proposals) are that "how."

Modeled on:
- **BIPs** (Bitcoin) — proposal numbering, status lifecycle, authoring conventions
- **EIPs** (Ethereum) — type categorization (Core/Networking/Interface/Meta/Informational)
- **PEPs** (Python) — discussion + sponsorship + acceptance criteria

Extended with:
- **Flux API integration** — the standard's executable surface is a `flux-api-*` crate. The PDF describes; the crate enforces. Both are generated from one source.
- **SAP-100% quality gate** — proposals must score 100% on Flux's SAP rubric (contribution / latency / stake / accuracy / uptime — repurposed for code/doc artifacts) before reaching Final.
- **LaTeX rendering** — proposals ship as Markdown for editing + LaTeX/PDF for archival + a Flux-API JSON for machine consumption. One source, three artifacts, all generated by `fluxc standard build`.

## FIP types

| Type | Examples |
|---|---|
| **Core** | New consensus rule (e.g. "every block carries a SQIsign nonce"), MIR semantics change |
| **Networking** | New gossipsub topic, libp2p protocol-id bump, transport addition |
| **Interface** | `flux-api` crate change, MCP tool surface, fluxc CLI |
| **Meta** | The FIP process itself (this doc is FIP-0001), governance change |
| **Informational** | Best-practice, threat model, design recommendation |

## Lifecycle

```
Draft → Proposed → Accepted → Final → (Superseded | Withdrawn | Rejected)
                                   │
                                   ▼
                          ratified into the Flux Standards Library
                          (printed in fluxc standard list)
```

Status transitions require **SAP-100% gate at every promotion** (Proposed → Accepted, Accepted → Final). The SAP rubric for an FIP:

| SAP dim | Means for a FIP |
|---|---|
| Contribution | Lines of substantive prose + code + tests vs cruft. Auto-scored by `fluxc standard score`. |
| Latency      | Median time-to-respond on issue thread. Bot-tracked. |
| Stake        | Number of `flux-swarm` agents formally co-sponsoring. ≥3 distinct wallets required for Accepted. |
| Accuracy     | All cited Flux APIs resolve; all benchmark claims reproduce within 10%; all code examples compile. |
| Uptime       | CI is green for ≥7 consecutive days against the proposal's reference implementation. |

100% = every dim ≥ 0.95. Below that, the FIP stays in Draft / Proposed. No exceptions for "trust me" — the metric is the gate.

## Auto-generation: `fluxc standard new`

A FIP starts as one CLI invocation:

```bash
fluxc standard new \
    --type core \
    --title "post-quantum block signature canonicalization" \
    --author rocky-sigil \
    --references FIP-0042,FIP-0107
```

Generates:
- `docs/standards/FIP-XXXX-<slug>.md` — Markdown template with all required sections
- `flux-api/standards/FIP-XXXX/Cargo.toml` — empty Flux API crate stub
- `flux-api/standards/FIP-XXXX/src/lib.rs` — `#[fip(XXXX)]` macro on a placeholder trait
- `tests/standards/FIP-XXXX/` — empty test folder, scored 0% SAP until populated

Auto-fills:
- Next available FIP number (atomic increment via swarm gossip — no conflicts even across concurrent authors)
- Date stamps
- Author wallet + signing block (proposer signs the proposal with their SIGIL/QUG key — proof of stake claim)
- Cross-references to cited FIPs validated to exist

## Auto-generation: `fluxc standard build`

```bash
fluxc standard build FIP-0042
```

From one Markdown source emits:
- `out/FIP-0042.html` — web-friendly view (obsidian + violet palette inherited from the dashboard)
- `out/FIP-0042.pdf` — LaTeX-rendered, archival quality, with `pandoc` → `xelatex`
- `out/FIP-0042.api.json` — Flux API spec extracted from `## API` section + the companion `flux-api/standards/FIP-XXXX/` crate
- `out/FIP-0042.sap.json` — SAP scorecard with sub-scores per dimension

## Flux API integration

Every FIP that changes behavior MUST ship a companion `flux-api/standards/FIP-XXXX/` crate. Two enforcement modes:

1. **Trait-level** — the FIP's behavioral surface is a trait. Implementations declare `impl Fip0042 for MyType { ... }` and a `#[fip_assert]` macro generates compile-time conformance tests.
2. **Conformance-test-level** — the FIP ships a parametric test suite. Any crate claiming conformance runs `flux-api-test fip-0042 my_crate` and gets a green/red.

This is the "the PDF describes; the crate enforces" pattern.

## LaTeX details

- `pandoc` for Markdown → LaTeX conversion (already in flux-arena toolchain)
- `xelatex` for typesetting (Unicode-safe — important for non-ASCII author names, math, emoji in code blocks)
- Custom Flux template `templates/fip.tex` with the obsidian + violet two-color scheme adapted to print (white background, violet headings + accent rules, JetBrains Mono for code)
- Section auto-numbering, table-of-contents, citations to other FIPs as PDF anchors
- Output: print-quality PDF suitable for inclusion in Flux Foundation enterprise-pilot deliverables

## SIGIL adoption

SIGIL chooses one of three relationships per FIP:

1. **Adopts** — runs the FIP's reference impl as-is. Default for Core / Networking / Interface FIPs that don't make chain-specific choices.
2. **Extends** — SIGIL ships a `sigil-` companion crate that subclasses the FIP API with SIGIL-specific behavior. Conformance to base FIP is preserved; SIGIL test suite extends.
3. **Declines** — SIGIL explicitly does not implement. Logged in `sigil/docs/sigil-flux-conformance.md` with a reason; the FIP authors can challenge.

Every SIGIL release ships `sigil-node fip-status` → table of every FIP and SIGIL's stance. Operators always know what their node honors. Future chains (sibling) inherit the same table.

## What this v0 deliberately does NOT include

- **A web FIP browser** — `quillon.xyz/standards/` listing all FIPs. P2. v0 ships local-CLI only (`fluxc standard list`, `fluxc standard view FIP-0042`).
- **A discussion protocol** — `https://github.com/<org>/flux-fips/issues/<n>` is the discussion channel for v0. Decentralized discussion (gossipsub-thread) is P3.
- **A formal voting layer** — Accepted vs Final is editor-judged (with the SAP-100% gate). On-chain SAP-weighted voting is P4.
- **Auto-translation to BIP/EIP format** — FIPs that cross-reference upstream BIPs link by URL. Bidirectional sync is out of scope.

## Open Qs

1. **Editor seats** — who has the "promote Draft → Proposed" privilege? Suggest **5-of-N multisig** on a Flux operator wallet (matches Bitcoin Core's commit-access culture; multisig matches Flux's chain-native idiom).
2. **Reference impl lifecycle** — if FIP-0042 ships a ref impl crate at v0.1 and FIP-0107 obsoletes it, does the crate stay published? Suggest: `cargo yank` the v0.1 with a redirect note to FIP-0107.
3. **Cross-chain conformance** — should there be a *Quillon* `q-node fip-status`? Quillon is on its own track but adopting FIPs would unify the substrate story. Suggest reaching out via cross-team broadcast after the v0 ships.
4. **SAP rubric thresholds** — 0.95 per dim is generous in the early days when there are few co-sponsoring agents. Suggest **graduated thresholds**: 0.80 for the first 10 FIPs (bootstrap), 0.90 for FIPs 11-50, 0.95 thereafter.
